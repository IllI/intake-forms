# Eaglesoft Integration Attempts Track Record

## What Actually Worked / Was Verified
1. **Database Reachability:** The database engine `EAGLESOFT` and database instance `DENTSERV` are actively reachable! We confirmed this by pointing the manual SQL connection at `ENG=EAGLESOFT; DBN=DENTSERV`. The database successfully responded, throwing `Invalid user ID or password`, effectively proving our SDK fallback *would* work if we had the actual secret password (which Patterson unfortunately changed from the `dba`/`sql` defaults on this specific database).
2. **Port 9888 / Swagger:** We successfully communicated with the `EaglesoftApiServer` on port 9888, verifying its `Swagger` specs. It is reachable, but requires a secret `IntegrationKey`.
3. **AppDomain Independence:** We successfully bypassed the System32 `TrustedInstaller` blocks by generating a self-contained `EaglesoftPS.exe` shell equipped with a raw WCF `App.config`. Although `PatientSvc` still dropped the `-999` error, we learned that PowerShell's entire `.NET` pipeline prevents the SDK from reading typical `appSettings` seamlessly.
4. **Native C# Executable (Failure):** We wrote a raw C# Payload (`IntakeWorker.cs`) to act as a wrapper, assuming compiling it as an `.exe` would restore the proper `.NET` configuration context. **This also failed.** While `new PatientSvc()` initialized cleanly, actually executing `CreatePatient()` triggered the exact same `-999 Pool Size Bug`. This proves the problem is NOT restricted to PowerShell's host; the SDK fundamentally relies on unmapped App/Global configs or registry keys that our standalone wrappers are failing to inherit.

## Moving Forward: The final blockers
1. **The Core Configuration Block**: The fundamental issue is that NO external script (no matter if it's PowerShell or a custom compiled `.NET` EXE) is inheriting Eaglesoft's expected global settings. The Patterson SDK dynamically constructs its `.mdf` or `.dsn` database connection string behind the scenes, and then it parses it looking for `Min Pool Size` or `Max Pool Size` parameter values (which default to empty/missing in our decoupled environment). Our next step MUST be decompiling the core SQL Initialization logic of the SDK using ILSpy, dotPeek, or `Reflector` to figure out PRECISELY which WCF `<connectionString>`, registry key path (`HKLM:\SOFTWARE\...`), or local `App.config` parameter it's parsing to build the string. Until we map that missing configuration, the entire SDK library is fundamentally unreachable outside of the internal Patterson UI thread.
2. **Missing `Document` class signature [SOLVED]:** We previously thought we lacked the `DocumentDto` class. Actually, our PowerShell reflection definitively established that `CreateDocumentFromFile` accepts a `Patterson.Services.DocumentService.Document` core object! The `IntakeWorker.cs` schema has been updated to successfully instantiate and populate this parameter signature safely.
